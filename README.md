# Financial CUA Benchmark

> A benchmark and verifier architecture for evaluating whether AI agents complete financial work—not merely generate plausible financial documents.

This repository is the cleaned public worktree for a Chinese financial Computer-Use Agent (CUA) evaluation project. It consolidates a financial-accounting task suite, deterministic verifier architecture, and a bond-underwriting workflow track under one project model.

## Project status: refactor in progress

The source workspace contains substantial working assets, but this repository is intentionally being rebuilt rather than copied wholesale. The current inventory distinguishes three levels of evidence:

| Level | What currently exists | What it does not prove |
| --- | --- | --- |
| Task specifications | 20 standard financial-accounting task packages, each with `task.md`, `SKILL.md`, and `verifier.md` | An end-to-end Agent run in a production-like environment |
| Deterministic verifier engine | A legacy framework with 21 registered modules, plus a clean public core with two independently refactored standard-task verifiers; legacy self-test returned golden `1.0` and initial `0.0` for all 21 modules, while the public core has synthetic unit tests | That the task instances, public release split, and real Agent evaluation protocol are complete |
| Adversarial probes | Documented mutation probes passed for five representative task families | Full adversarial coverage for every task or model benchmark results |

No model leaderboard, claimed pass rate, or end-to-end result will be published here unless it is generated by a documented execution protocol.

## What is being evaluated

The benchmark treats a task as a verifiable state transition:

```text
(t, c, s_init, s_gold, r)
```

| Element | Meaning |
| --- | --- |
| `t` | The task instruction visible to the Agent |
| `c` | The bounded context: entity, period, files, policies, output contract, and constraints |
| `s_init` | A reproducible starting environment |
| `s_gold` | The correct final business state, held separately from Agent-visible materials |
| `r` | A verifier that evaluates observable final state and returns a bounded score |

The intended claim is not that a financial professional can be replaced. It is that an Agent can be assessed for controlled, reviewable parts of financial work: structured filing, reconciliation, rule application, cross-file checks, evidence mapping, and draft preparation.

## Design principles

1. **Deterministic scoring first.** Numeric truth, equations, units, periods, completion, and observable state are checked deterministically whenever possible.
2. **Final business state over action traces.** The verifier evaluates what the Agent actually produced and submitted, rather than requiring one tool path.
3. **Evidence and provenance matter.** A correct total without field-to-source traceability is not a full success.
4. **Partial score with real failure gates.** Field coverage may earn partial credit; wrong scope, wrong period, tampering, an unsubmitted result, or a broken critical reconciliation can cap or fail the task.
5. **Human responsibility stays visible.** Domain judgment, professional conclusions, and external submission remain human responsibilities.
6. **Public development set, protected holdout.** Public examples must be synthetic or deliberately released development cases. Test instances and golden truth are managed separately to preserve benchmark meaning.

## Current refactor gate

Before this becomes the canonical public repository, the following work must be completed:

- normalize the 20-task catalog and separate the additional case-based finance-lease instance;
- move golden fixtures out of production task modules;
- replace real paths, contract identifiers, and embedded case values with a configurable synthetic case adapter;
- separate public task contracts from hidden truth and evaluation fixtures;
- align task-document status labels with actual engine and test evidence;
- migrate verifier code only after public API, test boundary, and package naming are stable; the first two standard-task migrations now establish that pattern.

This is deliberate: a polished benchmark should be honest about what is designed, what is implemented, and what has actually been executed.
